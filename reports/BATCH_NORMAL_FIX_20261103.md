# 批量标记正常925帧修复（2026-11-03）

## 实际根因

只读检查原项目 iGPUTest / 203机头 / Night.mp4：总1800帧、已确认207。875.000秒至1799.000秒是925个实际Frame UUID（从1开始的编号是876至1800），其中922帧unannotated、2帧带异常标注且confirmed、1帧normal且confirmed。原运行目录日志反复记录 START 批量标记正常，随后 Store.MarkNormalBatch 抛出“批次包含已标注或带异常框的帧，整个批次未提交”。因此按钮已触发，失败发生在全批拒绝的资格检查，不是只拿当前帧，也不是最后一帧提前return。原按钮读取RangeFrameList.SelectionIds，界面选择数也来自同一Ids集合。旧错误只进入共享底栏和日志，没有固定的批次成功/跳过/失败统计，用户难以确认结果。原全局草稿门槛还会使一个当前帧草稿阻止所有其他目标。

## 修复

按钮在UI线程立即捕获去重UUID快照，后台MarkNormalBatchEligible分类处理：仅未标注、未确认、无有效异常标注、未软删除及未审核锁定的帧进入原有严格事务；受保护帧逐项跳过并报告原因。合格帧仍统一走ApplyReview(normal, confirmed)、修订审计、清单写锁、冲突SHA、Flush(true)、File.Replace和失败内存/磁盘回滚。既有严格MarkNormalBatch保留，不改变IDS格式或单帧状态语义。

当前帧有未保存草稿时仅将它列入跳过，不阻塞其他帧，也不清除草稿。最后一帧与其他UUID同等处理。成功更新只修改相关Choice行与审核缓存，确认数由实际Review重算，不逐帧重建整表；筛选变化最多重建一次列表。新增固定批次反馈及进度，准备阶段明确“尚未提交”，只在原子提交返回后统计成功。失败使用中文原因并显示失败目标数；重复点击受busy保护，重复已确认帧不新增修订。

## 验证与交付

15项批量回归加1项独立新进程重开验证，均实际检查独立project.ids.json：单帧、3帧、跨滚动精确925 UUID、混合925、全部合格925、最后一帧、重复UUID/重复点击、异常框/多边形/ROI保留、软删除/审核锁、草稿保护、写锁失败、Flush后替换前异常、取消回滚、筛选与计数一致性。混合925结果为成功922、跳过3、失败0，确认数207→1129；全合格925则成功925。每批只一次事务提交。证据见 integration/batch-normal-20261103；本轮限定release_gate包含批量与既有1000/10000帧和IDS回归，无全量许可证审计。
